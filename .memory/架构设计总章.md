# 🧠 超级大脑架构总章（v2.1 规格基线 + v3.1.0 实现态）

> 定位：**本地优先的多端共享超级大脑**——为任意 Agent（WorkBuddy / CodeBuddy / Codex / DeepSeek-Harness / DSH 插件 / 自研 Agent）提供统一记忆服务；不同电脑经 GitHub 私有库自动同步；数据全程本地私有。
>
> ⚠ **阅读顺序（2026-11-11 更新）**：§一~§十四是 **v2.1/v2.2 规格基线**，其科学裁决（六引擎、事件溯源、双时态、RRF）仍有效，但目录树、页面名、发行形态与"唯一开发基准"的说法**已不再是当前实现**。
> **当前实现态是 §十五：v3.1.0 定稿架构**——Qt/PySide6 前端已整体删除，Flutter 为唯一前端；主进程是 `headless_server.py` 单进程三端口（8766 MCP / 8768 HTTP / 8767 WS）；MCP 能力面由 `gateway/tool_catalog.py` 单一真源提供（实测 **66 工具 / 6 resources / 59 rpcBacked**）。
> 改代码前先看 **§十五**，再回查前文裁决；v2.2 实现层增量见 §十四（页面名均为历史）。

## 一、总体形态：三平面架构

```text
┌────────────────── 接入平面（任意 Agent 动态注册，无白名单）──────────────────┐
│  WorkBuddy │ CodeBuddy │ Codex │ DeepSeek-Harness │ DSH插件 │ AstrBot │ 自研 │
│      MCP 适配器（主通道）＋ HTTP/OpenAI 兼容适配器（备通道）＋ 注册签发中心      │
└───────────────────────────────────┬──────────────────────────────────────┘
                                    ▼
┌────────────────── 认知平面（类脑核心，本地运行）───────────────────────────┐
│   丘thalamus门控 → 海马体(写入)/前额叶(召回) → 六引擎存储                  │
│   杏仁核PAD+好感度 │ 可塑性遗忘/强化 │ 分层晋升 │ 新皮层金字塔固化           │
└───────────────────────────────────┬──────────────────────────────────────┘
                                    ▼
┌────────────────── 同步平面（GitHub 事件总线，多脑合一）─────────────────────┐
│   本地事件日志(NDJSON) → GitHub私有库 → 各设备拉取重放 → 投影重建六引擎      │
└──────────────────────────────────────────────────────────────────────────┘
                                    ▼
              NiceGUI 神经活性看板（只读服务层）+ 昼夜节律生命循环
```

**总原则：六个逻辑引擎、五个物理基座（SQLite / LanceDB / Kùzu / LMDB / DuckDB），全部嵌入式零服务进程；认知层只依赖抽象接口；一切参数进 config；UI 与网关禁触存储。**

> **实现态修正（§十五）**：三平面仍是认知分工，但**物理进程已收敛为一个 Python 后端 + 一个 Flutter 进程**。
> "网关/UI/Worker/同步四方独立事件循环"已不成立：MCP 网关、v3 Worker、昼夜调度都在 `headless_server.py`
> 同一进程内共享一份 `build_app()`（Kùzu 单写者），UI 是独立进程、只走 WS RPC，不再有"UI 直连服务层"。
> 同步平面（journal + Git 事件总线）仍是可选能力，默认主链路是 v3 的 journal → inbox → Worker 异步消费。

## 二、科学性裁决（八条，含 v2.1 新增两条）

| # | 原案 | 裁决 | 理由 |
|---|---|---|---|
| 1 | 时序库 InfluxDB/TimescaleDB | **DuckDB** | 嵌入式列存 OLAP，零运维，窗口函数原生 |
| 2 | 超图独立库 MAGE/HypergraphX | **Kùzu 二部图编码 + HyperNetX 内存分析** | 无成熟可嵌入超图库；超边=事件节点+成员边，建模等价 |
| 3 | 另建 Meilisearch/Typesense | **LanceDB 原生 FTS + SQLite FTS5** | 不再养一个服务 |
| 4 | BGM3 / Qwen 0.6B | **BGE-M3（1024维）/ Qwen3-0.6B** | 型号更正；BGE-M3 一个模型同时给稠密+稀疏两路向量 |
| 5 | KNN 后过滤 is_active | **LanceDB 预过滤 ANN** | 标量过滤先于向量搜索，结构性根治漏召回 |
| 6 | ArcadeDB 多模态统一库 | 否决 | JVM 服务、驱动不成熟 |
| 7 | ★ Git 直接同步数据库文件 | **Git 只存事件日志，六引擎全部降级为投影** | 二进制库文件无法合并必然冲突；追加型事件流每设备只写自己目录，Git 合并退化为纯新增，结构性免冲突 |
| 8 | ★ 多端各存独立状态 | **全事件溯源：状态=事件日志的确定性投影** | 一切状态变更皆事件（写入/失效/强化/晋升/固化），重放幂等，任何设备可从日志重建完整大脑 |

## 四、存储引擎矩阵

| 引擎 | 基座 | 职责 | 关键规则 |
|---|---|---|---|
| 关系库 | SQLite + WAL | 元数据主库、双时态、outbox、FTS5 | 唯一事实源，写入先落此库 |
| 向量库 | LanceDB | 稠密1024 + 稀疏 + 全文三通道 | 预过滤ANN；维度读 config |
| 图谱 | Kùzu | 实体边、演进边、多跳扩展 | 超边=事件节点+成员边 |
| KV | LMDB | 画像槽位、精确键直读 | 只存单键确定性数据 |
| 时序 | DuckDB | PAD轨迹、访问/衰减事件 | 只写不改，夜间分析主战场 |
| 超图 | Kùzu + HyperNetX | 多Agent协作事件、高阶情景 | 逻辑独立，物理复用图谱基座 |

**并发纪律**：每引擎 thread-local 连接；SQLite WAL + busy_timeout；网关/UI/Worker/同步四方独立事件循环，跨层只走 asyncio 队列；连接对象禁止跨线程共享。

## 五、算力层三模型

| 模型 | 职责 | 运行时 | 降级 |
|---|---|---|---|
| BGE-M3 | 稠密1024维 + 稀疏权重 | ONNX Runtime | CUDA→CPU 自动 |
| bge-reranker-v2-m3 | 多路召回交叉编码精排 | ONNX Runtime | 同上 |

## 六、数据模型核心规格

**Neuron 必备字段**：`uuid7_id` / `device_id` / `agent_id` / `memory_type`（fact·code·scenario·emotion·profile 五类）/ `content` / `pad(p,a,d)∈[-1,1]` / `affinity`（好感度）/ `confidence`（信任梯度）/ `valid_from, valid_to`（事件时间）/ `transaction_from, transaction_to`（系统认知时间）/ `tier` / `strength, stability` / `namespace`（私有区·群组区·全局区）/ `is_active`。

**双时态语义**：valid_time 回答“事实在现实中何时成立”，transaction_time 回答“系统何时知道”——支持“我10月时认为X是什么”的时点查询。

## 七、科学机制规格

1. **遗忘曲线**：FSRS 三变量模型（难度D、稳定度S、可提取性R），R 随时间幂律衰减；参数由个人 DuckDB 访问日志离线再拟合。
2. **记忆曲线（强化）**：成功召回 → S 增长（间隔效应）；高频 + 高唤醒（PAD 的 A 分量）→ 巩固优先级提升。
3. **检索总分**：`score = w1·RRF名次 + w2·R新鲜度 + w3·突触强度 + w4·PAD显著性 + w5·置信度`，权重全进 config，靠 eval 调参。
4. **RRF 融合**：六路各自超采样 k×4 → 预过滤 is_active → `score(d)=Σ 1/(60+rank)`。
5. **信任梯度晋升**：confidence>0.95 且访问≥N次 → 核心层；0.5~0.95 → 召回层；<0.5 → 低权重参与 + 复核队列。
6. **分层 × 金字塔正交**：tier（缓冲→核心→召回→归档）按热度流动；pyramid（原始→事实→主题→世界观）按抽象度夜间升维。互不混用。
7. **冲突消解**：检测（同实体+同谓词+高相似）→ 裁决（置信度 + transaction_time）→ 处置（旧记录 valid_to 封存永不物理删除；图谱建 `supersedes` 演进边；低置信冲突入 Life Loop 复盘队列）。

## 八、同步平面：GitHub 私有库事件总线（v2.1 核心）

### 8.1 私库布局（免冲突设计）

```text
brain-sync/  （GitHub 私有库）
├── journal/
│   └── devices/{device_id}/          # ★ 每设备只写自己的目录 → 永无合并冲突
│       └── 20261105.seq.ndjson       # 追加式事件段，段满滚动
├── snapshots/
│   └── snapshot-{yyyymmdd}/          # 定期快照（新设备冷启动基础）
├── manifest.json                     # 设备注册表、各设备游标、schema_version、向量维度
└── POLICY.json                       # 命名空间与权限策略（随库同步，全局一致）
```

### 8.2 事件模型

| 字段 | 说明 |
|---|---|
| event_id | UUIDv7，全局幂等键，重放去重依据 |
| device_id / agent_id | 产出设备与来源 Agent |
| hlc | 混合逻辑时钟（物理ms + 计数器 + device_id），全序保证，时钟回拨免疫 |
| type | `ingest`(写入) / `supersede`(冲突失效) / `reinforce`(召回强化) / `tier_change`(晋升降级) / `consolidate`(金字塔升维/画像更新) / `policy`(策略变更) / `tombstone`(合规级删除标记) |
| payload | 实体完整快照 + 向量（含维度版本，随 manifest 校验） |
| schema_version | 事件结构版本，投影器据此兼容 |

**确定性要求**：可塑性变量（S/R）不作为随机状态存储，而是由 `reinforce` 事件流在读取时确定性计算——保证任意设备从同一日志重放出完全一致的大脑状态。

### 8.3 同步循环（每设备）

```text
写入请求 → 本地投影六引擎（立即可读）→ 追加本地事件段(fsync) → 延迟防抖
git_worker（定时N分钟 + 写入触发）：
  git pull → 扫描各设备新事件段 → HLC 排序 → event_id 幂等重放 → 投影更新
  → 提交本地新事件段并 push → 清理已快照覆盖的旧段
断网：本地照常读写，恢复后自动补推（本地优先，永不阻塞认知层）
```

### 8.4 关键机制

| 机制 | 规格 |
|---|---|
| 缓冲层不同步 | tier=缓冲的工作记忆只留本地（人脑工作记忆亦不跨脑同步），晋升为核心/召回层时才产生跨设备事件 |
| 冲突收敛 | 两台设备同时写入矛盾事实 → 各自产生 `ingest` 事件 → 重放后由冲突消解机制统一裁决（supersede + 演进边），两端最终一致 |
| 快照与压缩 | 段大小阈值 + 月度归档；快照=某 HLC 切点的全量投影清单；新设备冷启动 = clone → 载入最新快照 → 重放尾部日志（分钟级全量重建） |
| 容量账 | 单事件≈文本+1024维向量：float32≈4KB；可选 int8 量化≈1KB。1~5 万条记忆 50~250MB，Git 完全可控；10 万条级启用量化 + 分段归档，必要时 LFS |
| 安全 | 细粒度 PAT（仅该私库 contents 读写），存系统钥匙串/env，禁入库与事件；私库本身私有；敏感内容可选 age 对称加密后才入 journal（各设备持钥，端到端）；事件内禁含任何密钥 |
| 时延 | GitHub 轮询=分钟级（间隔可调）。近实时为可选增强：局域网/Tailscale 直连某主机的 MCP 端点，接口已预留，默认不引入中心服务器 |

## 九、多 Agent 接入设计（任意 Agent）

### 9.1 注册中心（registry）

|---|---|

## 十四、记忆可视化与用户控制（v2.2 实现层补充）

> 本节是对实现态的补充说明，不改动前面七阶段的架构裁决；决策理由见 `DECISIONS.md` ADR-011~014。

### 14.1 用户控制 = 既有事件的重组（不新增事件契约）

| 用户动作 | 事件 | 效果 | 审计 |
|---|---|---|---|
| 纠正 / 编辑 | 新 `ingest` + 旧 `supersede`（payload 带 before/after/actor/reason） | 新版本生效；旧行 `is_active=0` + `tx_to/valid_to` 打点，原值不改 | `memory_audit()` 可就地看到前后值 |
| 封存 | `tombstone`（`action="archive"`）或 `tier_change` → archive | 从常规召回退出，保留可追溯 | 审计里按 `action` 区分遗忘/封存 |
| 遗忘 | `tombstone` | 主库 deactivate + `vector.delete`：推理路径彻底消失 | 事件与封存行保留 |

写入顺序固定 `journal.append(fsync) → 主库 → 派生库 / outbox → dispatch`；
因为复用 7 类事件，`EventProjector` 与跨设备重放无需改动。
**不做物理删除**：物理删了之后落后设备重放 `ingest` 会把记忆复活；合规硬清除需另设 purge 流。

### 14.2 可视化分区

## 情绪记忆全链路（PAD 贯穿位置）

| 环节 | 所在模块 | PAD 的作用 |
|---|---|---|
| **生成** | `router_extractor` + `amygdala` | 写入时 LLM 估算三维 PAD：愉悦度 P / 唤醒度 A / 支配度 D ∈ [-1,1]，杏仁核负责精算与好感度低通积分 |
| **建模** | `models/neuron.py` | 每条记忆自带 `pad(p,a,d)` 字段 + `affinity` 慢变量 + `memory_type='emotion'`（五类记忆之一） |
| **存储** | SQLite + DuckDB | 元数据存 SQLite；**PAD 波动轨迹只写不改入 DuckDB 时序库**，可查“某段时间情绪曲线” |
| **检索** | `prefrontal` 总分公式 | `w4·PAD显著性`——高唤醒（|A|大）的记忆在召回排序中被加权，对应“情绪增强记忆”的心理学事实 |
| **巩固** | `synaptic_plasticity` | 高唤醒事件稳定度 S 增长更快（闪光灯记忆效应），衰减更慢 |
| **生命循环** | `life_loop` | 夜间情绪复盘：DuckDB 轨迹分析 → 情绪趋势报告 → 异常波动触发记忆复查 |
| **同步** | `sync/journal` | `ingest / reinforce / consolidate` 事件的 payload 携带 pad 与 affinity，**多端情绪状态同步一致** |
| **可视化** | `ui/panels` | PAD 时间轴面板、好感度曲线、情绪-记忆关联视图 |

## 情绪边界（对照图中你原有设计的落点）

- **好感度 affinity** = P 维度的时间积分慢变量：单次情绪事件只是波动，长期正/负交互才改变好感度；
- **召回偏置**：好感度影响前额叶注入的语气参数与记忆配额（高好感 Agent 的历史正面记忆召回权重上调）；
- **情绪边界规则**：高负唤醒事件可触发“冷静期”策略——短期压制该 Agent 相关记忆的召回优先级，避免情绪污染上下文。

## 一个闭环示例

Agent A 与用户发生冲突 → `save_memory` 写入，LLM 估出 P=-0.7, A=0.8 → 杏仁核记录并微降好感度 → 该记忆因高唤醒获得巩固加速与召回加权 → 夜间 Life Loop 在 PAD 轨迹上标出该波动点 → 三天后另一台电脑上的 Agent B 查询相关话题，同步层已把这条“情绪着色”的记忆带给它，前额叶据此注入“该话题用户曾有负面体验，收敛措辞”的指令。

这块目前是规格级设计（机制、字段、权重位都已定义）。需要细化到杏仁核的 PAD 估算规则与好感度积分公式级别时，说一声即可。
